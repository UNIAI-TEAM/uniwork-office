| Tag            | Meaning                                                                                                                                                                                                                                                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

## 0. Summary

1. **Every preload method is accounted for** (section 1): `pdfApi` 54 methods, `markdownApi` 36, `htmlApi` 48, plus `projectApi` (4, identical in
   all three), `installDropOpenBridge()` (preload side effect of all three) and the two non-preload globals the renderers touch (`window.open`, `window.print`).
   Call-site counts are regenerated by the script in appendix A.
2. **Protocol additions needed: two optional fields, one server flavour, no new message type.**
   (a) `InitPayload.user?: {displayName}` (PDF note author; also useful for Docs), (b) `OpenPayload.assets?` (path -> url map) so that Markdown/HTML
   documents with relative images (`assets/x.png`) display on reopen (section 3.4), (c) the existing frame request `api.export {format:'pdf', html}`
   (payload field `html` already exists) needs a **host route flavour** that accepts an HTML body; today the dev-uniwork `/export/pdf` route takes a docx.
   Read-only viewers need no new field: the host simply does not grant `save` (to be wired in the frame, see 2.4). `file.pick` multi-select
   (PDF merge) is avoidable by repeated single picks.
3. **PDF is the only module with structural work.** The whole save pipeline (`applySaveRequest`, annotation delete, text/image edit, form values,
   stamps, page ops) lives in `apps/pdf/src/main` and is bytes-in/bytes-out over pdf-lib + pdfium wasm, but it reads wasm/fonts with `fs`, uses
   Electron `nativeImage` and `Buffer`. The renderer additionally assumes a path on disk (`readFile(path)` after every save). The port is an
   injection job (3.1), not a rewrite. Markdown and HTML are text documents: their bridge is small (open, save, saveAs, images, export, print).
4. **CSP/security conflicts (explicit list, details in 3.3 and 3.5, measured in Chromium 151 under the Docs header):**
   - **C-1 `script-src 'self'` blocks every WebAssembly compile/instantiate** (main thread and worker). PDF needs `'wasm-unsafe-eval'`
     (pdfium for annotation delete / text edit / image edit; pdf.js codecs). Desktop `apps/pdf/src/renderer/index.html` already carries it. **PDF module CSP must differ from the Docs CSP** (contract C3 allows it if the module says why: this is why).
   - **C-2 the three renderer `index.html` files carry a `<meta http-equiv="Content-Security-Policy">`** (desktop). The web entries must not (header-only CSP, `frame-ancestors`).
   - **C-3 HTML preview cannot run scripts or the inspector inside a nested `srcdoc` frame**: a srcdoc/blob frame inherits the embedding page's CSP, so the inline
     inspector `<script>` (`instrument.ts:22`) and any document script are blocked (measured). Desktop previews with `sandbox="allow-scripts allow-forms allow-popups allow-modals"` and **network allowed**; G3 previews with a strictly _tighter_ sandbox on a separate preview origin. Visual edit and "scripts on" need either that preview origin (`frame-src <origin>`) or stay hidden.
   - **C-4 same-origin frame + untrusted HTML**: the B2B3 security note applies fully. Document-rendering paths must not inject raw HTML into the frame DOM. Findings: Markdown is safe by construction (schema parse) except Mermaid SVG injected with `dangerouslySetInnerHTML`; HTML is _not_ rendered in the frame DOM, only in the preview frame, which therefore must be sandboxed without `allow-same-origin` and (preferably) `credentialless`.
   - **C-5 remote images**: `img-src 'self' data: blob:` blocks `https:` images in documents (also inside srcdoc). G3 behaves the same. Keep, document, and optionally inline through `image.fetch` at insert time.
   - **C-6 print/export iframes**: `srcdoc` frames are _not_ blocked by `frame-src 'none'` (measured); `blob:` frames are. Markdown print can keep its hidden srcdoc frame.
5. **Builds (section 4): all three plain `vite build` renderer configs succeed** (6.2 s / 21.5 s / 5.1 s wall on the shared box). Blockers are not build errors but web-readiness:
   no `base: './'` in the plain configs (I passed `--base ./`), PDF output relies on `viteStaticCopy` into `pdfjs/` (169 CMaps, 16 standard fonts, wasm + fallbacks; 3.3 MiB raw), Markdown emits 59 KaTeX font files in three formats each (1.02 MiB; the Docs WOFF2 plugin does not run here) and ~60 lazy Mermaid chunks.
6. **G3 parity (section 2):** switching must not lose view-only mode, the password prompt, find, thumbnails, notes/forms/signatures/stamps (PDF); Source/Visual toggle, outline, find/replace, math/diagrams, frontmatter, byte-identical open->save of raw HTML/comments (Markdown: **not kept by the frame**, measured in 3.4: HTML comments are dropped and `<div>` wrappers unwrapped on first save); Source/Split/Preview/Present and print (HTML). The frame **gains** PDF text edit, replace image, insert/extract/merge pages, page-size/crop/n-up (all unsupported in the G3 browser lane today) and HTML visual edit / docx+PDF+single-file export, but only if the matching capability keys are turned on.

## 2. What the G3 host offers today, and what the frame must keep

G3 = dev-uniwork `OfficeEditorHost` + per-format adapters (`apps/web/platform/office/{pdf,md-html}-adapter.tsx`, `pdf-office-host.tsx`) and the views in
`packages/views/office/{pdf,markdown,html}`. Save is the shared coordinator: serialize -> upload (`uploadDocumentFile`) -> commit
(`commitDocumentVersion` with `base_revision` and idempotency key) = **one new Documents version per save**, conflict -> typed state, durable browser
draft recovery (`DraftRecoveryPrompt`), leave dialog, save status. The genoffice frame saves through `api.save {etag}` (same server commit), conflict
dialog in the frame, leave dialog in the host.

### 2.4 Switch-without-regression checklist (host + frame)

1. View-only documents open view-only in the frame (host withholds `save`; frame hides edit UI). Needs a task in each module (not present in desktop code).
2. Size gate and `too_large` state before any byte reaches the frame (host: reuse `readDocumentBytesWithinBound` semantics in the open route).
3. Password-protected PDFs prompt in the frame and never send the password to the host.
4. Same save semantics: one version per explicit save, stale etag -> frame conflict dialog (Docs `F1`), dirty guard + leave dialog in the host, no autosave.
5. Fallback: G3 stays the editor when the module bundle is not installed/verified or the flag is off (contract C4/C5) - and, for Markdown/HTML, a one-way switch must not rewrite documents differently from G3 (3.4 fidelity).
6. The frame never shows a command whose backend is missing (capability keys, section 5.2).

## 3. Format specifics

### 3.1 PDF: where the bytes go on save

**Everything the user does is written into the PDF; there is no sidecar.** `SavePdfRequest` (`apps/pdf/src/shared/ipc.ts:127`) carries pending overlays
that `applySaveRequest(bytes, request)` (`apps/pdf/src/main/save-pdf.ts:864`, bytes in, bytes out) applies in a fixed order:

| Stage                                                                             | What is written                                                                            | Engine                                                                                           |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| `annotDeletes`                                                                    | removes saved highlight/underline/strikeout/note annotations                               | **pdfium** (`annot-delete.ts` -> `loadPdfium`)                                                   |
| `textEdits`, `textInserts`                                                        | content-stream text rewrite / new text objects, subset fonts                               | **pdfium** + harfbuzz subset wasm + **OS font files** (`text-edit.ts:152-254`, `font-subset.ts`) |
| `imageEdits`                                                                      | content-stream image ops (move/resize/crop/flip/replace)                                   | **pdfium** + Electron `nativeImage` (`image-edit.ts:72,373,445`)                                 |
| `markups`, `drawings` (ink, shapes, image stamps), notes (+ replies, `noteEdits`) | real PDF annotations (`/Highlight`, `/Ink`, `/Square`, `/Stamp`, `/Text` with `/IRT`)      | pdf-lib                                                                                          |
| `formValues`, `staticFormFills`                                                   | AcroForm field values; GenOffice static-fill metadata stored inside the PDF                | pdf-lib                                                                                          |
| `stamps`                                                                          | renderer-rasterised bitmaps embedded and positioned (watermark/header/footer/page numbers) | pdf-lib                                                                                          |
| `rotations`, `deletedPages`, `pageOrder`, `metadata`                              | page tree and Info dictionary                                                              | pdf-lib                                                                                          |

The result is the **complete rewritten file** (pdf-lib `save`; untouched objects are kept, not reordered), then `verifyContentEdits`, then an atomic write.
Each web save therefore uploads the whole PDF as a new Documents version (a 50 MiB PDF saved 10 times = 500 MiB of versions; same as G3).
The renderer then **re-reads the file and calls `getDocument` again** (`App.tsx:937`), keeps overlays only until that reload, and reads from disk again for print (`App.tsx:4902`).

**Port shape (no rewrite):** a browser module `web/modules/pdf/` that (1) imports `applySaveRequest` and the page-op `*Bytes` functions, (2) supplies the
four Node-only seams: `loadPdfium()` (`text-edit.ts:124`: `readFileSync(pdfiumWasmPath())` -> `fetch('pdfium.wasm')`, 4.6 MiB raw), `loadHb()`
(`font-subset.ts:31`, harfbuzz subset wasm), font bytes (`text-edit.ts` candidates -> a font set shipped as build assets, or text edit hidden), and
`nativeImage` (-> OffscreenCanvas), and (3) replaces `Buffer` (14 uses in `text-edit.ts`, 7 in `font-subset.ts`/`font-cmap.ts`) with a polyfill or
`Uint8Array`. Without pdfium the pdf-lib stages still work: a **v1 without text/image edit and without deleting _saved_ annotations** is possible
(`pdfTextEdit`, `pdfImageEdit`, `pdfAnnotDelete` capability keys); adding annotations, forms, stamps, signatures, rotate/delete/reorder and page ops
needs no wasm in the frame save path. dev-uniwork already has a browser pdfium lane (`@uniwork/office-engine/browser`: `loadBrowserPdfium`,
`applyPdfOpsInBrowser`, wasm copied to `public/office/pdfium.wasm`) which refuses text edit/replace image/insert/extract/merge; it is a design reference,
not a drop-in (different op model).

### 3.2 PDF: large files

- G3 gate: 64 MiB (`ENGINE_LIMITS.max_input_bytes`, `packages/office-contracts/src/limits.ts:8`), checked from the download descriptor before transfer.
  The frame must not accept more than the host allows; the host answers `api.open` with `too_large` (existing code) so the frame shows its error state.
- Transport: `FileSource {kind:'bytes'}` transfers the `ArrayBuffer` (no copy) and `{kind:'url'}` must be same-origin (CSP `connect-src 'self'`). v1 = bytes.
  pdf.js range loading (`getDocument({url, httpHeaders})`) would avoid holding the file twice but the content route is Bearer-only and the token stays in the client closure: out of scope for B4.
- Memory (estimate, **not measured**): working copy + the copy handed to the pdf.js worker (pdf.js transfers, so a copy is needed) + pdf-lib's parsed object
  graph during save (typically several times the file size) + the re-read after save. Plan for roughly 4-6x the file size at peak per tab; the 64 MiB gate
  bounds it near 400 MiB. A measured number belongs in the B4 e2e (one 50 MiB fixture).
- Rendering is lazy per page (`PdfPage.tsx`, IntersectionObserver-style windowing is the renderer's existing behaviour); print rasterises at up to 200 DPI with a pixel budget (`print.ts` `MAX_PRINT_PIXELS`), thumbnails use `PdfThumb`.
- Save time scales with file size and runs on the main thread of the frame (pdf-lib is synchronous-heavy): run `applySaveRequest` in a dedicated worker (`worker-src 'self'` allows a bundled worker file) so the UI does not freeze on large files.

### 3.3 PDF: pdf.js worker, wasm, CMaps, standard fonts under CSP

Setup in the renderer: `GlobalWorkerOptions.workerSrc = workerUrl` (`App.tsx:254`, `import ... pdf.worker.min.mjs?url`), `DOC_OPTS` (`view-config.ts:31-36`)
points `cMapUrl`, `standardFontDataUrl`, `wasmUrl` at `new URL('pdfjs/', document.baseURI)`, copied by `viteStaticCopy` in both renderer configs.
Built output (section 4): worker `assets/pdf.worker.min-*.mjs` (1.25 MiB, same-origin file) and `pdfjs/{cmaps (169 files, 1.11 MiB), standard_fonts (16, 0.74 MiB), wasm (4 `.wasm` 0.88 MiB + 3 JS fallbacks + licences, 1.47 MiB)}`.
Everything is a hashed or fixed same-origin file; nothing is inlined and there is no `eval` in the app bundle (the one `new Function` in Markdown is jszip's setImmediate polyfill, as in Docs).

**Measured** with `web/docs/build/csp.ts` header verbatim (`default-src 'none'; script-src 'self'; ... worker-src 'self'; frame-src 'none'; ...`),
Chromium 151 headless, a Node server sending the CSP on every response, real `pdfjs-dist` 6.2.108 legacy build + `@embedpdf/pdfium` 2.15 wasm. Variant **a** = Docs CSP, **b** = a +
`'wasm-unsafe-eval'` in `script-src`, **c** = b + `frame-src 'self'`. Harness: appendix B.

| Probe                                                                                                  | a (Docs CSP)                                       | b (+wasm-unsafe-eval) | c (+frame-src 'self')                             |
| ------------------------------------------------------------------------------------------------------ | -------------------------------------------------- | --------------------- | ------------------------------------------------- |
| `WebAssembly.instantiate` main thread                                                                  | **blocked** (`script-src <- wasm-eval`)            | ok                    | ok                                                |
| `WebAssembly.instantiate` inside a same-origin module worker                                           | **blocked**                                        | ok                    | ok                                                |
| `WebAssembly.compile` of the real `pdfium.wasm` (4.6 MiB)                                              | **blocked**                                        | ok                    | ok                                                |
| pdf.js: open + render page + text layer, same-origin worker, CMaps/fonts/wasm urls set (text-only PDF) | ok, 0 violations                                   | ok                    | ok                                                |
| `new Worker(blob:)`                                                                                    | blocked (`worker-src <- blob`)                     | blocked               | blocked                                           |
| iframe `srcdoc` (plain / `sandbox=""` / `credentialless`)                                              | **loads** (not blocked by `frame-src 'none'`)      | loads                 | loads                                             |
| iframe `blob:`                                                                                         | blocked (`frame-src <- blob`)                      | blocked               | **still blocked** (`'self'` does not cover blob:) |
| srcdoc + `sandbox="allow-scripts"` + inline `<script>`                                                 | **script blocked** (inherited `script-src 'self'`) | blocked               | blocked                                           |
| remote `https://` `<img>` inside srcdoc                                                                | blocked (`img-src`)                                | blocked               | blocked                                           |

Conclusions:

- **C-1 (blocking for PDF save paths that use pdfium):** the PDF module CSP needs `script-src 'self' 'wasm-unsafe-eval'`. This is not `unsafe-eval` (no JS eval); the desktop
  `apps/pdf/src/renderer/index.html` already says so ("pdf.js image codecs (jbig2/openjpeg/qcms)"). Document it in the module's `csp.json` `notes`.
  pdf.js itself renders without it (measured on a text PDF); its JPX/JBIG2/ICC codecs and the form-scripting sandbox (`quickjs-eval.wasm`, 458 KiB) use wasm and
  ship `*_nowasm_fallback.js` files, so a no-wasm CSP should degrade rather than fail (not exercised). **Not exercised here:** a PDF with JPX/JBIG2 images, an embedded-font PDF (font-face
  path), XFA/JS forms. They belong in the B4 e2e fixtures and must run with zero `securitypolicyviolation` events like `web/e2e/csp-header.spec.ts`.
- `worker-src 'self'` is enough for pdf.js (the worker is an emitted same-origin asset). Do not allow `blob:` workers; a bundled worker for `applySaveRequest` is also `'self'`.
- Fonts: the Docs rule (`font-src 'self'`, no data: URIs) holds; desktop's meta also allows `data: blob:` - drop that. pdf.js `standard_fonts/*.ttf` are fetched (`connect-src 'self'`); embedded fonts go through `FontFace(ArrayBuffer)` (verify with the embedded-font fixture).
- Headers: the Docs host headers apply to every `/office-frame/` path; for the pdf module the pinned CSP differs in exactly one token (C3 `csp.json` per module), `worker` file responses must carry it too (a worker's CSP comes from its own response).

### 3.4 Markdown and HTML: images, links, sanitisation, fidelity

**Images and relative links.** Desktop authors a relative path (`assets/<name>`) after copying the file next to the document (`pickImage`/`saveImage`) and
shows it through custom schemes (`md-asset://`, `html-asset://`, path-jailed in main). The web has no sibling directory. Proposed mapping, consistent with G3
(`image-upload.ts`: only the relative path is authored, never a bucket name or URL):

1. Insert: frame calls `api.images.upload {fileId, name, mimeType, data}` (existing; returns `{imageId, url}` with a same-origin signed url) and authors `assets/<name>`; keeps `path -> url` for display.
2. Reopen: the host supplies the document's asset manifest in `OpenPayload` -> **NEW optional `assets?: {path, url}[]`** (additive, absent = none). Without it a document with
   relative images opens with broken images; inlining data URLs on save is rejected (megabyte lines; desktop HTML deliberately avoids it, `single-file-html.ts`).
3. `readImage` (docx export) and `loadImageDataUrl` fetch the mapped same-origin url; remote `https:` images are blocked by CSP (C-5).
4. Relative links to other documents are not resolvable on the web; links open only through `guardedOpen` (http/https), everything else is a no-op. The tiptap Link extension keeps `openOnClick:false` (`extensions.ts:31`); its default URI allow-list rejects `javascript:`
   (probe below).

**Sanitisation (same-origin frame, B2B3 security note).**

| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

**Fidelity probe (Markdown, genoffice editor, jsdom, real `buildExtensions`):** input = heading, `<!-- keep me -->`, `<div class="x" onclick="alert(1)">hi <b>there</b></div>`, `<script>alert(1)</script>`, `<img src=x onerror=alert(1)>`, `[js](javascript:alert(1))`, a remote `![r](https://evil.example/p.png)`. Serialised output: `# T\n\n\n\nhi **there**\n\n\n\n![](x)\n\n[js](javascript:alert(1))\n\n![r](https://evil.example/p.png)`. Findings: (a) the **HTML comment is dropped** and the `<div>` is unwrapped (attributes gone, `<b>` becomes `**`): raw HTML in the body is **not preserved**, unlike G3's byte-identical `markdownRaw` node, so a one-way switch can silently rewrite a document on first save (data-loss gap, goes into the e2e fixtures and decision 3); (b) `<script>` is dropped with its content and `onclick`/`onerror` attributes never reach the doc: nothing executable survives into the DOM or the saved text; (c) a `javascript:` link stays in the model as authored text but a second probe (`getHTML()` of a read-only editor) renders it as `href=""` (tiptap Link default allow-list), other links get `target=_blank rel="noopener noreferrer nofollow"`; (d) the remote image stays an image node (blocked at load by `img-src`, C-5). Method: a throwaway vitest file in `apps/markdown/tests` using the real `buildExtensions` (jsdom), run once and deleted, not committed.

### 3.5 HTML: what the preview does and why it conflicts

Desktop: the renderer pushes the buffer (`updatePreview`), main serves `html-preview://view-<id>/` (`preview-protocol.ts`; a `<base>` pointing at `html-asset://` is injected, `buildPreviewDocument`),
and `PreviewFrame.tsx` embeds it with `sandbox="allow-scripts allow-forms allow-popups allow-modals" referrerPolicy="no-referrer"`. The origin is opaque (no
`allow-same-origin`), but **scripts and network are allowed** ("CDN-dependent pages must render"), and the inspector is an inline `<script data-gx-inspector>` appended to the preview copy
(`instrument.ts:22`) that talks to the app with `postMessage(..., '*')`. Desktop CSP (`index.html`): `frame-src html-preview:`; `img-src ... file: html-asset:`.

Web conflicts (measured in 3.3 unless noted):

1. **A nested `srcdoc`/blob frame inherits the embedding page's CSP.** Inline `<script>` (the inspector and any document script) is blocked, and `https:` images/stylesheets/scripts are blocked
   by `img-src`/`default-src 'none'`. So "scripts on + network", the inspector, visual edit and click-to-select **cannot work in srcdoc under the Docs CSP**.
2. A relaxed CSP for the module is the wrong fix: any `script-src 'unsafe-inline'`/`https:` added to the frame page weakens the whole frame, which is same-origin with UniWork.
3. `window.postMessage(..., '*')` from the sandboxed frame is origin `"null"`; the frame's listener checks `event.source === contentWindow` only (`PreviewFrame.tsx:39-45`), no nonce. G3 uses a `MessageChannel` port + per-session nonce (`preview.ts`, `acceptPreviewMessage`).
4. Opaque-origin + `allow-forms` + `allow-popups` + network lets a hostile document submit forms and open windows with the user's ambient browser state; on desktop there is no ambient session, on the web there is.

Options (decision needed from the lead, recommendation first):

| Option                                                                                                                                                      | What                                                                                                                            | Cost                                                                                 | Risk                                                         |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| **P1 (recommended v1)**: static preview in `srcdoc`, `sandbox=""` (+ `credentialless`), no scripts, CSP-limited images (data:/blob:/same-origin asset urls) | works under the unchanged Docs CSP (measured); matches G3's default (scripts off)                                               | `htmlPreviewScripts` and `htmlVisualEdit` false; present mode static                 | lowest; documents that need scripts/CDN show unstyled/static |
| **P2**: reuse the G3 preview broker (separate preview origin, nonce'd inspector over `MessageChannel`, scoped asset proxy, CSP in the copy) from the frame  | needs `frame-src <preview-origin>` in the html module CSP, a host API to open a preview scope (`createPreviewScope`), asset ids | large (preview.ts is ~400 lines + host broker); enables scripts + visual edit safely | moderate, mostly integration                                 |
| P3: desktop parity (`allow-scripts allow-forms allow-popups allow-modals`, network on) on the app origin                                                    | blocked by CSP (1) and unsafe even if unblocked                                                                                 | -                                                                                    | **reject**                                                   |

HTML inside the **Markdown** preview/print uses the same rules (static).

3. **PDF static assets depend on `viteStaticCopy`** (`pdfjs/cmaps|standard_fonts|wasm`), which is not part of the Docs build pipeline (`web/docs/build/plugin.ts` manifest hashing). The manifest must hash these (not under `assets/` / `fonts/`, so the immutable-cache rules for hashed dirs need `pdfjs/**` added) and `build:web` must keep them out of the "never inline" rule.
4. **Markdown ships KaTeX fonts three times** (woff2 + woff + ttf per face). The Docs `woff2FontsPlugin` rewrites faces to WOFF2 only; reusing it would drop the woff/ttf duplicates (about two thirds of the 1.02 MiB, estimate).
5. **Markdown bundle weight**: the initial chunk is 2.03 MiB (i18n dictionaries are 4097 lines in one `strings.ts`; 19 languages, same lever as Docs) and Mermaid adds ~60 lazy chunks, which is fine for caching but means the manifest has ~120 files.
6. `pdf.worker.min` is emitted as a hashed `.mjs`: the host must serve `.mjs` with a JavaScript MIME type (`frame-headers.mjs` precedent for `.js`; verify `.mjs`).
7. Typecheck/tests were not run (analysis lane); `apps/{pdf,markdown,html}/tests` exist for the pure parts (`save-pdf`, `docText`, `ops`).

The scanner (not committed as a file: this document is the only deliverable); run from the repo root after `npm ci`:

```js
// node scan.mjs <app> <global>   e.g. pdf pdfApi | markdown markdownApi | html htmlApi
import fs from 'node:fs'
import path from 'node:path'
const [app, glob] = process.argv.slice(2),
  root = `apps/${app}/src`
const walk = (d, o = []) => {
  for (const e of fs.readdirSync(d, { withFileTypes: true })) {
    const p = path.join(d, e.name)
    e.isDirectory()
      ? walk(p, o)
      : /\.(tsx?|js)$/.test(e.name) && !/\.test\./.test(e.name) && o.push(p)
  }
  return o
}
const pre = fs.readFileSync(`${root}/preload/index.ts`, 'utf8'),
  a0 = pre.indexOf('const api')
const methods = [...pre.slice(a0, pre.indexOf('\n}\n', a0)).matchAll(/^  ([a-zA-Z]+):/gm)].map(
  (m) => m[1],
)
const hits = {}
for (const f of walk(`${root}/renderer`)) {
  const src = fs.readFileSync(f, 'utf8')
  for (const m of src.matchAll(new RegExp(`${glob}\\s*\\??\\.\\s*([a-zA-Z]+)`, 'g')))
    (hits[m[1]] ||= []).push(
      `${f.replace(`${root}/renderer/`, '')}:${src.slice(0, m.index).split('\n').length}`,
    )
}
for (const m of methods)
  console.log(m, (hits[m] || []).length, (hits[m] || []).slice(0, 3).join(' '))
console.log(
  'not in preload:',
  Object.keys(hits).filter((k) => !methods.includes(k)),
)
```
